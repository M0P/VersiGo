## Findings

- [High] `apps/worker/src/paperless-tag.client.ts:64-67` (with `apps/worker/src/worker.module.ts:44`) — `PaperlessTagClient` is a plain class provider without `@Injectable()`, so Nest cannot resolve its `SettingsResolverService` constructor dependency and the whole worker-side tag sync is non-functional at runtime.

  - Evidence: `WorkerModule.providers` registers `PaperlessTagClient` as an ordinary class provider, but the class has **no decorator at all** (grep for `@Injectable` over `apps/worker/src` returns only the two `@Processor(...)` classes) and only the two processors have decorators. `apps/worker/tsconfig.json` sets `emitDecoratorMetadata: true`; TypeScript only emits `design:paramtypes` for a declaration that carries a decorator, so `Reflect.getMetadata('design:paramtypes', PaperlessTagClient)` is `undefined` and Nest's injector falls back to `new PaperlessTagClient()` with no arguments. Additionally the import is type-only (`import type { SettingsResolverService } from '@versigo/foundation'`, line 4), which would break the metadata reference even after adding the decorator. Consequence: `runtimeConfig()` dereferences `this.settings.getEffectiveBoolean(...)` on `undefined`. `handleSyncPolicy` and `handleTagDocument` call `await this.client.baseUrl()` / `assignTagToDocument(...)` at the very start of processing, so every `SYNC_POLICY`/`TAG_DOCUMENT` job throws inside `process()`'s try/catch and returns `{success:false}`. Because `WorkerHost` resolves instead of throwing and `removeOnComplete: true` is set, the BullMQ job is discarded; the durable row stays `PENDING` and `handleReconcile` re-dispatches it every 60 s forever. The net effect is AP-22's core behaviour (auto-assignment by tag, tagging of manually linked documents) never works in the worker, while the unit test passes because `paperless-tag.processor.spec.ts` constructs the processor with a hand-made client object, and the API still returns 200 (no bootstrap error), so compose smoke would not catch it either.

  - Required fix: Decorate the class with `@Injectable()` and import `SettingsResolverService` as a value (not `import type`) so `emitDecoratorMetadata` can reference it; add a worker smoke/DI test (or an integration check) that bootstraps the module and asserts tag jobs actually reach the Paperless client.

- [Medium] `apps/api/src/features/documents/documents.service.ts:430-439` (with `apps/api/src/features/paperless-ngx/paperless-tag.service.ts:246-251`) — the round-4 removal of the `linkOriginTag` short-circuit is complete, but the remaining `taggingStatus === 'APPLIED'` short-circuit is still not tag-version aware, so a manual link can silently never receive the newly configured tag.

  - Evidence: `applyManualLinkOrigin` skips job creation and returns without an outbox row whenever `document.taggingStatus === 'APPLIED'`, on the stated assumption that this state is "self-healed by setTag's reset on tag change". That reset only matches rows with `linkOriginManual: true` (`paperless-tag.service.ts:246-251`: `{ policyId, linkOriginManual: true, taggingStatus: 'APPLIED' }`). Reachable sequence: (1) tag A configured, document X manually linked → `APPLIED`, `linkOriginManual: true`; (2) a later A-sync sets `linkOriginTag: true` on X (dual origin, still `APPLIED`); (3) the user removes the manual link — the round-1/2 dual-origin branch in `remove()` (verified in the diff, `~582-600`) clears only `linkOriginManual`, leaving `taggingStatus = 'APPLIED'`, so X is now live with `linkOriginManual: false`; (4) the admin changes A→B — `setTag`'s reset misses X because `linkOriginManual` is false; (5) the B-sync clears `linkOriginTag` but never resets `taggingStatus`, and the user (re-)links X manually → `applyManualLinkOrigin` sees `APPLIED` and queues **no** `TAG_DOCUMENT` job. X is then excluded from `scheduleManualLinkBackfill` (`OR: [{ taggingStatus: null }, { taggingStatus: { not: 'APPLIED' } }]`, `paperless-tag.processor.ts:5025-5035`) and from `retryTagging` (`taggingStatus: { in: ['PENDING','FAILED'] }`) forever, until the tag is changed a second time. This is the same failure mode the round-4 fix removed for `linkOriginTag`, silently violating "Beim nachträglichen Konfigurieren/Wechseln … erhalten bereits manuell verlinkte Paperless-Dokumente ebenfalls diesen Tag".

  - Required fix: Only skip job creation when the `APPLIED` state is provably valid for the **current** configuration version/tag (e.g. persist the config version the tag was applied for), or drop the short-circuit and rely on `assignTagToDocument`'s own "tag already present → no-op" path; additionally reset `taggingStatus` for rows whose manual origin was removed, or make `setTag`'s reset cover `linkOriginTag: true` rows too. Add a regression test for remove-manual → tag change → (re-)link → assert a `TAG_DOCUMENT` job.

- [Minor] `apps/api/src/features/paperless-ngx/paperless-ngx.service.ts` `assignTagToDocument` — the fallback branch still returns `NOT_FOUND`, so `NOT_FOUND` can be produced by a document assignment even though the round-4 fix reserved it for tag lookups.

  - Evidence: the missing-document case now returns `DOCUMENT_NOT_FOUND` (line ~652), but later in the same method the read-merge-write fallback's failure path still uses `NOT_FOUND` for a missing document while the worker client mirrors the same branch with `DOCUMENT_NOT_FOUND`. The interface comment (`paperless-ngx.interface.ts`) documents the codes as identical to the worker client's, and `docs/04-data-model.md` states `NOT_FOUND` means "deleted tag".
  - Required fix: Mirror the worker client's code in that branch (`DOCUMENT_NOT_FOUND`) so `NOT_FOUND` is only ever produced by tag lookups.

- [Minor] `apps/web/src/app/policies/[id]/paperless-tag-section.tsx:100-107` — the tag-search spinner can stay stuck.

  - Evidence: the debounced search effect sets `setSearching(true)` only on the "long enough" path; when the term is shortened below 2 characters it runs `setResults(null); return;` without clearing `searching`. The effect cleanup cancels the pending timeout, so no request ever completes and the guarded `finally` never runs — the `{searching && <InlineSpinner />}` block remains visible indefinitely after e.g. typing "ab" and deleting to "a".
  - Required fix: clear the searching flag in the short-circuit branch (and on unmount) so the spinner reflects only in-flight requests.

- [Minor] `apps/api/src/features/paperless-ngx/paperless-tag.service.ts:486-490` — leftover draft comment left in shipped code.

  - Evidence: inside `retryTagging`'s loop the comment reads "…Re-enqueue the existing job (idempotent at the transport level after durable re-enqueue) … Created list will be empty for this doc; we enqueue existing outside the loop. A small adjustment: collect existing ids." — it describes the author's editing process and is partly wrong (the branch does `created.push({ id: existing.id })` immediately below), which will confuse maintainers.
  - Required fix: Replace it with a factual explanation of why an existing active job is re-enqueued, or delete it.
