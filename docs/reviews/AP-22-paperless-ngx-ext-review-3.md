## Findings

- [Medium] `apps/api/src/features/paperless-ngx/paperless-tag.service.ts:300–342` (removeTag) + `:246–251` (setTag) — "Tag entfernen" leaves stale per-document tagging state on every manual link that has **no** tag origin; the R2 fix only covered dual-origin rows.
  - Evidence: Both `policyDocument.updateMany` calls in `removeTag` are constrained to `linkOriginTag: true` (branch 1: `{policyId, linkOriginTag: true, linkOriginManual: false}` → archive, line 319; branch 2: `{policyId, linkOriginTag: true, linkOriginManual: true}` → `linkOriginTag: false, taggingStatus: null`, line 323). A row with `linkOriginManual: true, linkOriginTag: false` is matched by neither. That state is the *normal* state right after a manual link: `applyManualLinkOrigin` (`apps/api/src/features/documents/documents.service.ts:~414–476`) only sets `linkOriginManual`, and the worker's `handleTagDocument` confirms the assignment with `{ taggingStatus: 'APPLIED' }` without ever setting `linkOriginTag` (`apps/worker`-side file, `paperless-tag.processor.ts:418–422`). Consequences after "Zuordnung entfernen":
    1. *PENDING/FAILED stays forever.* Configure a tag, manually link a document, remove the tag while the assignment is still pending (or failed because Paperless was unreachable): the document keeps `taggingStatus = PENDING`/`FAILED`. The documents tab keeps rendering the "Tag-Zuweisung ausstehend/fehlgeschlagen" badge (`apps/web/src/app/policies/[id]/documents-tab.tsx:~515–527`) and a "Tag-Zuweisung wiederholen" button (`:555–556`) whose handler (`:466`) always fails, because `retryTagging` (`paperless-tag.service.ts:453` ff.) throws `NotFoundException('NO_PAPERLESS_TAG_CONFIGURED')` when no config exists — the UI turns that into the generic `common.unknownError`.
    2. *A later tag is never applied.* A row that is stuck at `taggingStatus = 'APPLIED'` with `linkOriginTag = false` is excluded from `scheduleManualLinkBackfill` (`OR: [{ taggingStatus: null }, { taggingStatus: { not: 'APPLIED' } }]`, `paperless-tag.processor.ts:343`) and from `retryTagging` (`taggingStatus: { in: ['PENDING','FAILED'] }`). Re-assigning a tag afterwards does not recover it either: `removeTag` deleted the config row, so in `setTag` the reset is skipped (`if (existing && existing.paperlessTagId !== tagId)`, line 246 — `existing` is `null`) and a subsequent `setTag` with the *same* id also skips it; even re-linking short-circuits on `taggingStatus === 'APPLIED'` (`documents.service.ts:~433`). The manual link therefore never receives the newly configured tag and shows no badge, silently violating "Beim nachträglichen Konfigurieren eines Tags erhalten bereits manuell verlinkte Paperless-Dokumente ebenfalls diesen Tag".
  - Required fix: Make `removeTag` reset the per-document tagging state for *all* remaining manual links of the policy (not only those that currently carry `linkOriginTag`), e.g. clear `taggingStatus`/`taggingErrorCode` for every `linkOriginManual: true` row with a non-null tagging status, and/or make `setTag` reset `APPLIED`→`PENDING` also when the configuration is newly created. Add a regression test for: configure tag → manual link (PENDING/FAILED and APPLIED variants) → remove tag → assert no `taggingStatus` remains, plus remove-tag → re-assign tag → assert the manual link is re-queued for the new tag.

- [Minor] `apps/api/src/features/paperless-ngx/paperless-tag.service.ts:54–76` — the periodic reconcile tick is registered only by the API app.
  - Evidence: `PaperlessTagService.onModuleInit` is the only place that adds the repeatable `PAPERLESS_TAG_RECONCILE_JOB`; `WorkerModule` registers the queue/provider but never registers the tick. If Redis is unavailable during API bootstrap the `queue.add` throws, is swallowed, and neither the periodic background sync nor the re-dispatch of PENDING outbox rows resumes until an API restart (the worker cannot recreate it).
  - Required fix: Register (or re-register) the repeatable tick from the worker as well, or retry the registration from a periodic safe point instead of relying solely on API bootstrap.

- [Minor] `apps/worker/src/paperless-tag.processor.ts:224` with `:258/:308` and `:361–374` — the manual-link backfill runs even when the reconciliation aborted due to a stale configuration and writes an unversioned `taggingStatus: 'PENDING'`.
  - Evidence: `reconcileAssignments` returns early when `fresh.configVersion !== configVersion` (`:258`, `:308`), but `handleSyncPolicy` still marks the job `COMPLETED` and calls `scheduleManualLinkBackfill(policyId, job.configVersion)` (`:224`). The backfill's `policyDocument.update` in the transaction (`:361`) is not guarded by the current config version, so documents can be left `PENDING` with only `STALE_CONFIG`-skipped jobs (the subsequent backfill skips them because an active PENDING job exists). It self-heals at the next successful sync, but the job is reported as successfully completed although it aborted mid-walk.
  - Required fix: Propagate the abort out of `reconcileAssignments` (or re-check the config version before the backfill/`COMPLETED` update) so an aborted reconciliation is not reported as completed and does not write stale pending states.

- [Minor] `apps/api/src/features/documents/documents.service.ts:~414–476` (`applyManualLinkOrigin`) — a redundant external tagging job is queued for rows that already carry the tag.
  - Evidence: When the existing row is tag-origin (`linkOriginTag: true`) with `taggingStatus: null` (the row created by `reconcileAssignments`), a manual link sets `taggingStatus: 'PENDING'` and creates a `TAG_DOCUMENT` job although the document provably already carries the tag in Paperless (that is why the row exists). This costs an extra Paperless GET and briefly shows a wrong "pending" badge; it is not a wrong assignment (`assignTagToDocument` short-circuits when the tag is present).
  - Required fix: Skip job creation (and the PENDING state) when the row already has `linkOriginTag: true`, or derive the initial state from the tag origin instead of always assuming PENDING.

- [Minor] All new files are added with mode `100755` (executable).
  - Evidence: `paperless-tag.service.ts`, `paperless-tag.processor.ts`, `paperless-tag.client.ts`, the DTO/constant/controller files, the new `__tests__/*.spec.ts`, `migration.sql` and `prompts/AP-22-paperless-ngx-ext` are all recorded as `new file mode 100755`. TypeScript sources and SQL/markdown do not belong in the executable bit set.
  - Required fix: Normalize the file modes to `100644` for the new source, SQL, test and documentation files.

- [Minor] `docs/04-data-model.md` (PaperlessTagJob `errorCode` list, added block at the end of the model section) — the documented code set is incomplete relative to what the worker actually writes.
  - Evidence: The doc lists `STALE_CONFIG, CONNECTION_CHANGED, TAG_REMOVED, UNREACHABLE, SYNC_FAILED, VERIFY_FAILED, DOCUMENT_GONE, SUPERSEDED`, but the worker additionally writes `POLICY_ARCHIVED` (`paperless-tag.processor.ts:~130`), `AUTH_FAILED`/`NOT_CONFIGURED`/`NOT_FOUND` (lookup kinds, `:150`) and `API_ERROR`/`UNKNOWN` (`:431`).
  - Required fix: Extend the documented error-code list (or reference the single source of truth) so operators can interpret `syncErrorCode`/`taggingErrorCode` completely.
