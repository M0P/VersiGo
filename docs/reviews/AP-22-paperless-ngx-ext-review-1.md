## Findings

- [High] `apps/worker/src/paperless-tag.processor.ts:342` (and `apps/api/src/features/documents/documents.service.ts:431`) — A tag change never retags already-`APPLIED` manual documents, and the backfill query also excludes `taggingStatus = NULL`.
  - Evidence: `scheduleManualLinkBackfill` selects `NOT: { taggingStatus: 'APPLIED' }` and is the only mechanism that adds the configured tag to manual links. On a tag change (`setTag`) only `policyPaperlessTag.configVersion` is incremented; no `PolicyDocument.taggingStatus` is reset. Documents that were retagged for the *previous* tag stay `APPLIED`, so they are excluded from the backfill and never receive the new tag — directly contradicting the work package ("Tag ändern: Ergänze den neuen Tag bei allen manuell verlinkten Paperless-Dokumenten"). The same filter also matters for `linkPaperlessDocument`, which short-circuits when `document.taggingStatus === 'APPLIED'`. Additionally, the filter `NOT: { taggingStatus: 'APPLIED' }` relies on Prisma/SQL null semantics: `NOT (col = 'APPLIED')` is `NULL` (not `TRUE`) for rows where the column is `NULL`, so pre-existing manual links created before a tag existed (the BugFix-07 rows with `taggingStatus = NULL`) are also excluded from the first backfill. This is the exact scenario "Beim nachträglichen Konfigurieren eines Tags erhalten bereits manuell verlinkte Paperless-Dokumente ebenfalls diesen Tag". The unit test only mocks the `findMany` result, so it does not catch either facet.
  - Required fix: Add an explicit "not applied to the *current* tag" condition (e.g. `OR: [{ taggingStatus: null }, { taggingStatus: { not: 'APPLIED' } }]`) and make the APPLIED state tag-aware. Reset per-document `taggingStatus` (to `PENDING` or `NULL`) for the policy's manual links when the tag actually changes, so the backfill re-queues them; add a regression test that a version bump re-queues a previously `APPLIED` document.

- [Medium] `apps/api/src/features/paperless-ngx/paperless-tag.service.ts:148-171` + `apps/web/src/app/policies/[id]/paperless-tag-section.tsx:83` — `getConfig` returns `null` for an unconfigured policy; Nest's Express adapter writes an empty 200 body for `null`, and the frontend `res.json()` throws, producing a false "could not be loaded" error.
  - Evidence: `getConfig` returns `null` when no `PolicyPaperlessTag` exists (the normal state for every existing policy). `@nestjs/platform-express` `ExpressAdapter.reply` uses `isNil(body)` → `response.send()`, i.e. an empty body with HTTP 200. In `paperless-tag-section.tsx`, `loadConfig` only checks `res.ok`; `await res.json()` then throws `Unexpected end of JSON input`, which is caught and rendered as `policies.paperlessTagLoadError`. So every policy without a tag shows a spurious error alert next to the (still usable) selection UI. No other controller in the API returns `null`, so this path is new and untested.
  - Required fix: Return a stable shape (e.g. `{ configured: false }`) from `getConfig` (or make the frontend use `res.json().catch(() => null)` and treat `null`/empty as "not configured"), and add a service/controller test for the unconfigured case.

- [Medium] `apps/api/src/features/documents/documents.service.ts:544-592` × `apps/web/src/app/policies/[id]/documents-tab.tsx:1110` — Removing a manual link on a document that is *also* tag-assigned archives the whole local row (both origins), so the document disappears until the next successful sync, contrary to the confirm dialog and requirement.
  - Evidence: For `linkOriginTag && linkOriginManual` the UI shows the normal "Löschen" button, whose confirm text (`paperlessDeleteBothConfirm`) states "only the manual link is removed; the automatic assignment via the tag remains". The endpoint called is `DELETE .../documents/:docId` → `DocumentsService.remove`, which unconditionally sets `archivedAt` on the single row that carries both `linkOriginManual` and `linkOriginTag`. `findAll` filters `archivedAt: null`, so the document vanishes immediately and only reappears when `reconcileAssignments` re-creates an auto row at the next sync (up to 5 minutes, or a manual "Jetzt aktualisieren"). While archived, the doc is also lost to `reconcileAssignments`' `localByRef`, so it is re-created as a fresh row (new id, metadata re-fetched).
  - Required fix: On removal, if the row has `linkOriginTag`, clear only `linkOriginManual` (keep the row and the tag origin); archive only when no automatic origin remains.

- [Medium] `apps/web/src/app/policies/[id]/paperless-tag-section.tsx:90-107` vs `apps/worker/src/paperless-tag.processor.ts:189/199` — The UI maps `TAG_DELETED`, but the worker never emits it; a tag deleted in Paperless is reported to the user as "Unbekannter Fehler beim Abgleich".
  - Evidence: `handleSyncPolicy` writes `syncErrorCode = lookup.error`, whose values are `NOT_FOUND | AUTH_FAILED | NOT_CONFIGURED | UNREACHABLE`, plus `SYNC_FAILED` and `CONNECTION_CHANGED`. The frontend `errorLabel` switch has a case for `TAG_DELETED` (and the docs/data-model list `TAG_DELETED`), but no case for `NOT_FOUND`, so the deleted-tag case falls through to `paperlessTagErrorUnknown`. The requirement explicitly asks for a comprehensible warning and to distinguish a deleted tag from missing permissions.
  - Required fix: Either emit `TAG_DELETED` from the processor for the `NOT_FOUND` lookup, or add a `NOT_FOUND` case to `errorLabel` (and remove the dead `TAG_DELETED`/`paperlessTagRetried` keys or wire them up).
