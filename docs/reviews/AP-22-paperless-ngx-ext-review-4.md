## Findings

- [Medium] `apps/api/src/features/documents/documents.service.ts:443-458` (with `apps/worker/src/paperless-tag.processor.ts:313-317`, `apps/api/src/features/paperless-ngx/paperless-tag.service.ts:245-250`) — the round-3 `linkOriginTag` short-circuit trusts a stale flag: a manual link can be marked `APPLIED` and never receive the configured tag.
  - Evidence: the new branch (`applyManualLinkOrigin`) treats `document.linkOriginTag === true` as proof that "the document provably carries it already" and therefore sets `{ linkOriginManual: true, taggingStatus: 'APPLIED' }` and queues **no** job. But `linkOriginTag` is set by `reconcileAssignments` (processor `:313-317`) **without recording which `configVersion`/tag it was verified against**, and neither `setTag` (`paperless-tag.service.ts:245-250`, resets only rows that are already `linkOriginManual: true`) nor `removeTag` clears it. Concrete sequence: tag A is synced and creates a tag-origin row for doc X (`linkOriginTag: true`); the user switches to tag B (`setTag` queues a sync but leaves X's `linkOriginTag` untouched); while the B-sync has not yet succeeded (or Paperless is unreachable), the user manually links X → branch sets `APPLIED`, no job. The B-sync then clears `linkOriginTag` (manual preserved, `processor.ts` second loop) but leaves `taggingStatus = 'APPLIED'`, so `scheduleManualLinkBackfill`'s `OR: [{ taggingStatus: null }, { taggingStatus: { not: 'APPLIED' } }]` excludes X forever, and `retryTagging` targets only `PENDING`/`FAILED`. The document silently never receives tag B — a direct violation of "Beim nachträglichen Konfigurieren eines Tags erhalten bereits manuell verlinkte Paperless-Dokumente ebenfalls diesen Tag" and "Tag ändern: Ergänze den neuen Tag bei allen manuell verlinkten … Dokumenten". Before round 3 this case was handled correctly (a redundant but harmless job was queued); the fix traded an inefficiency for a correctness gap.
  - Required fix: only skip the job when the tag origin is provably valid for the **current** configuration (e.g. persist the `configVersion`/tag id that the tag origin was verified against and compare it), or drop the short-circuit entirely and rely on `assignTagToDocument`'s own "tag already present → no-op" guard. Add a regression test: sync tag A → change to tag B (no successful B sync) → manual link → assert a `TAG_DOCUMENT` job (or an `APPLIED` state only when the tag was verified for B).

- [Medium] `apps/worker/src/paperless-tag.processor.ts:443-456` — `handleTagDocument` never checks for Paperless connection drift, so a pending manual-link job can add the policy tag to an unrelated document on a *different* server.
  - Evidence: `handleSyncPolicy` compares `config.connectionRef` with `client.baseUrl()` and terminates with `CONNECTION_CHANGED` (processor `:396-402` region), and `docs/06-integrations.md:46` claims "Zeigt `PAPERLESS_URL` auf einen anderen Server als `connectionRef`, werden Jobs als `CONNECTION_CHANGED` beendet und die Zuordnungen bleiben unangetastet (kein stilles Verschieben auf einen fremden Server)". `handleTagDocument` only validates the config **version**; it then calls `client.assignTagToDocument(Number(document.storageRef), config.paperlessTagId)` against whatever `PAPERLESS_URL` currently is. A TAG_DOCUMENT row created before an admin repointed Paperless (e.g. queued while the worker was down, then re-dispatched by the reconcile tick after restart) therefore uses the old numeric document id and old tag id against the new server: it can mark a wrong document on the foreign instance with the VersiGo tag (whose suggested name reveals the insurer: `VersiGo – <Versicherungsname>`) and set local `taggingStatus = APPLIED`. This also violates the explicit requirement "Vor jeder Verarbeitung prüfen, ob Verbindung und Konfigurationsversion noch aktuell sind." (Not a regression of round 3 — it predates it — but it is part of this work package and contradicts the documented invariant.)
  - Required fix: perform the same `config.connectionRef !== await this.client.baseUrl()` guard in `handleTagDocument` (skip with `CONNECTION_CHANGED`, mirroring `handleSyncPolicy`) before any external call, and add a processor test for a TAG_DOCUMENT job under a changed connection.

- [Minor] `apps/api/src/features/paperless-ngx/__tests__/paperless-tag.service.spec.ts:300` — malformed test line (broken formatting) that a format/lint gate will flag.
  - Evidence: `it('creates the configuration for a policy without a tag', async () => {      db.policyPaperlessTag.findUnique.mockResolvedValue(null);` — the statement is glued to the opening brace on one over-long line, which `prettier` (and any `pnpm run lint` step that includes a format check) will reformat/fail.

- [Minor] `docs/04-data-model.md:122-131` — the "complete" `errorCode` list is still incomplete and inconsistent with what is actually written.
  - Evidence: the list enumerates `… NOT_FOUND, DOCUMENT_GONE, VERIFY_FAILED` and states it is "identisch für `PaperlessTagJob.errorCode` und `PolicyDocument.taggingErrorCode`". The worker client's 404 path emits `DOCUMENT_NOT_FOUND` (see the processor's own test `fails permanently on a non-retryable error`, which asserts `taggingErrorCode: 'DOCUMENT_NOT_FOUND'`), while the API adapter emits `NOT_FOUND` for the same condition. `DOCUMENT_NOT_FOUND` appears nowhere in the list, and the API/worker codes for the same failure differ.
  - Required fix: add `DOCUMENT_NOT_FOUND` to the documented list (or unify the two adapters on one code) so operators can interpret `taggingErrorCode`/`errorCode` completely.
